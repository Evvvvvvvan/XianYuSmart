# 闲鱼平台写操作风控护栏设计

## 目标

在不影响平台读取、WebSocket 自动回复、Cookie 更新和滑块验证的前提下，为高风险 MTOP 写操作增加账号级限流与 `RGV587` 自动熔断，阻止并发任务持续重复请求并扩大平台风控。

护栏只能减少触发频率、在触发后及时止损，不能保证平台永远不返回风控，也不替代平台要求的账号验证。

## 范围

受限写操作采用明确的 API 白名单：

- 商品发布：`mtop.idle.pc.idleitem.publish`
- 商品下架：`mtop.taobao.idle.item.downshelf`
- 商品删除：`com.taobao.idle.item.delete`
- 商品擦亮：`mtop.taobao.idle.item.polish`
- 订单评价：`mtop.taobao.idle.merchant.rate.create`
- 小刀免拼：`mtop.idle.groupon.activity.seller.freeshipping`
- 订单发货：`mtop.taobao.idle.logistics.merchant.consign.dummy`
- 兼容订单发货：`mtop.taobao.idle.logistic.consign.dummy`

以下调用不进入写限流：

- 商品、订单、评价、会话资料等读取接口
- WebSocket 自动回复、发货私聊和图片消息
- Cookie 自动续期、人工粘贴更新与扫码更新
- 自动或人工滑块验证
- Token 刷新和 WebSocket 重连

## 方案

复用现有 `RiskControlService` 作为统一护栏，由 `XianyuApiCallUtils` 在所有 MTOP 调用的公共入口执行检查，不在各业务服务中重复实现。

限流维度为“账号 ID + API 名称”。同一账号、同一种写操作每 60 秒允许一次；不同写操作使用独立桶，因此小刀免拼不会占用订单发货额度，商品发布也不会阻塞评价或擦亮。

限流采用固定 60 秒滑动窗口。由于容量为 1，只需记录每个桶最近一次已放行时间，不引入第三方限流依赖。

## 调用流程

1. `XianyuApiCallUtils` 判断 API 是否属于写白名单。
2. 首次写请求先检查账号熔断状态。
3. 熔断未开启时检查对应 API 桶的最近放行时间。
4. 有可用额度时记录本次放行时间并请求平台。
5. 无可用额度时不请求平台，直接返回护栏结果和剩余等待秒数。
6. Token 过期后的同一业务请求重试复用首次额度，不重复消耗写额度。
7. 任意 MTOP 响应命中风控标志时，立即为账号开启熔断。

## 风控识别与熔断

统一识别以下平台风控标志：

- `RGV587`、`RGV587_ERROR`
- `FAIL_SYS_USER_VALIDATE`
- `FAIL_SYS_ILLEGAL_ACCESS`
- `FAIL_BIZ_WUA_IS_MACHINE`、`WUA_IS_MACHINE`
- `被挤爆`、`哎哟喂`
- `punish`、`captcha`

账号命中任一标志后开启 10 分钟写熔断。熔断期间：

- 写白名单调用直接拒绝并返回剩余时间。
- 读取调用继续执行，用于状态查询和业务展示。
- Cookie、滑块、Token 和 WebSocket 恢复链继续执行。
- 新的风控响应可以延长该账号熔断结束时间，但不能缩短已有时间。

## 状态持久化

限流时间和熔断结束时间写入 `data/platform-risk-guard.json`。生产容器已有 `/app/data` 持久卷，因此应用重启后继续遵守剩余限流和熔断时间。

状态文件写入要求：

- 使用 Java 标准库和项目现有 Jackson，不增加依赖。
- 临时文件写完后原子替换正式文件，避免中途退出留下半个 JSON。
- 文件不存在、内容损坏或单条数据过期时忽略无效状态并记录不含凭证的警告。
- 所有状态变更在进程内使用同一把锁，保证并发检查与写入的原子性。
- 状态只保存账号 ID、API 名称和时间戳，不保存 Cookie、Token、请求参数或平台响应。

## 恢复行为

熔断在以下两种情况下解除：

1. 10 分钟冷却期自然结束。
2. 人工粘贴 Cookie、扫码更新或滑块验证成功，通过 `AccountService.updateAccountCookie` 保存完整凭证后立即解除。

普通 MTOP `Set-Cookie` 合并只调用 `AccountService.updateCookie`，不能解除熔断，避免一次局部 Token 刷新错误地恢复高风险写操作。

解除熔断不清空最近写入时间，同一种写操作仍需遵守剩余的 60 秒间隔。

## 业务失败语义

`XianyuApiCallUtils.ApiCallResult` 增加护栏状态和剩余等待秒数，使调用方可以区分平台失败与本地护栏拒绝。

- 手工操作返回“写操作过于频繁，请 N 秒后重试”或“账号风控冷却中，剩余 N 秒”，不伪造平台调用结果。
- 自动评价遇到限流或熔断时停止当前账号本轮处理，不把未请求平台的订单记录为评价失败。
- 自动擦亮遇到限流或熔断时停止当前账号本轮处理，等待下一轮调度。
- 小刀免拼与订单发货使用不同 API 桶，正常连续流程互不占用额度。
- 平台已经收到请求但返回未知结果时仍按现有业务逻辑处理，护栏不修改订单成功状态。

## 日志与可观测性

日志记录以下事件：

- 写请求被限流，包含账号 ID、API 名称和剩余秒数。
- 账号熔断开启，包含账号 ID、风控类型和熔断结束时间。
- 写请求被熔断拒绝，包含账号 ID、API 名称和剩余秒数。
- 完整凭证更新后熔断解除。

日志不得记录 Cookie、Token、完整请求参数或平台敏感响应。

## 验证标准

临时测试覆盖：

- 同一账号、同一写 API 的第二次调用在 60 秒内被拒绝。
- 同一账号的不同写 API 互不影响。
- 不同账号的同一写 API 互不影响。
- 读取 API 不受写限流影响。
- 命中 `RGV587` 后后续写调用在请求平台前被拒绝。
- 熔断期间读取、Cookie 更新和滑块恢复不受影响。
- 完整凭证更新立即解除熔断。
- 普通 `Set-Cookie` 合并不会解除熔断。
- 状态保存后重新创建服务仍能读取剩余熔断和限流时间。
- 损坏的状态文件不会阻止应用启动。
- Token 刷新后的同一写请求重试不重复消耗额度。
- 自动评价被护栏拒绝时不写入平台失败状态。

## 影响范围

开发侧仅修改统一风控服务、统一 MTOP 调用入口、完整凭证更新解除点和自动评价护栏语义；不修改 WebSocket 消息链、滑块拖动实现、商品读取、订单读取、数据库表结构及现有部署拓扑。

使用侧的正常单次操作保持原流程；同一账号在一分钟内重复执行相同写操作时会看到明确等待时间，命中平台风控后高风险写操作暂停，账号验证或 Cookie 更新成功后恢复。
