# Cookie 粘贴引导与账号标识兼容设计

## 目标

- 在滑块验证的“粘贴 Cookie”方式中恢复原四步引导和“访问闲鱼 IM”入口。
- 接受没有 `unb`、但 `havana_lgc2_*` 中包含有效 `hid` 的 Cookie。
- 保存后的 Cookie 继续兼容现有 WebSocket、Token、订单和其他平台调用，不扩散修改范围。
- 不记录、展示或提交完整 Cookie、令牌及解码后的敏感字段。

## 方案比较

### 方案一：现有弹窗增加引导子页面，公共工具兼容账号标识（采用）

“粘贴 Cookie”先进入现有滑块弹窗的引导子页面；后端公共 Cookie 工具负责提取账号标识并补齐兼容字段。改动集中，原有自动拖动和人工拖动不受影响，现有下游逻辑无需逐处修改。

### 方案二：直接打开手动更新弹窗并默认展开帮助

改动更少，但无法完整恢复原“访问闲鱼 IM”流程，帮助内容与粘贴表单混在一起，仍缺少从验证到粘贴的连续操作。

### 方案三：所有下游调用分别兼容 `hid`

不修改保存内容，但 WebSocket、Token、订单等多个调用点都要增加回退解析，重复代码多且容易遗漏，不采用。

## 前端交互

1. 滑块验证弹窗继续显示“全自动拖动、人工拖动、粘贴 Cookie”三种方式。
2. 选择“粘贴 Cookie”并点击操作按钮后，不直接关闭弹窗，而是显示原四步引导：
   - 访问闲鱼 IM 页面。
   - 在闲鱼页面完成滑块验证。
   - 按 F12 打开开发者工具并复制最新 Cookie。
   - 返回连接管理并继续粘贴 Cookie。
3. “访问闲鱼 IM”通过新标签打开 `https://www.goofish.com/im`，引导页保持打开。
4. “继续粘贴 Cookie”沿用现有事件打开 `ManualUpdateCookieModal`，不新增重复表单。
5. 手动更新弹窗的重要字段提示改为：`unb` 或 `havana_lgc2_*`，并继续提示 `_m_h5_tk`、`cookie2`、`t`。

## 后端处理

在 `XianyuSignUtils` 增加统一账号标识处理：

1. 优先读取 Cookie 的 `unb`，保持旧格式完全兼容。
2. 缺少 `unb` 时，查找 `havana_lgc2_*` Cookie。
3. Base64 解码其 JSON，只读取数字格式的 `hid`；无效 Base64、无效 JSON、空值或非数字值均视为无法识别。
4. 保存前在 Cookie 末尾补齐 `unb=<hid>`，已有 `unb` 时不重复添加。
5. 手动更新账号、手动新增账号和浏览器验证回收 Cookie 共用该处理，避免同类入口结果不一致。

补齐 `unb` 只用于兼容项目现有调用链，值来自同一份平台 Cookie 内的 `hid`，不生成或猜测账号标识。

## 错误处理

- `unb` 与有效 `hid` 都不存在时，返回“无法从 Cookie 中识别账号信息，请确认包含 unb 或有效的 havana_lgc2 字段”。
- 解析失败不修改账号、Cookie、Token 或连接状态。
- 日志只记录账号 ID 和失败类型，不记录 Cookie、`hid` 载荷或令牌。

## 验证范围

- 现有 `unb` Cookie 仍可提取并保存。
- 仅包含 `havana_lgc2_*` 的脱敏测试 Cookie 可提取 `hid` 并补齐 `unb`。
- 无效 Base64、无效 JSON、缺少 `hid`、非数字 `hid` 均被拒绝。
- 已有 `unb` 时不重复添加。
- 前端正式构建通过，三种验证方式均可正常切换。
- 粘贴方式可完成“引导 → 打开闲鱼 IM → 继续粘贴 → 保存并重连”闭环。

## 影响范围

- 前端：滑块验证弹窗、手动 Cookie 更新提示。
- 后端：Cookie 公共解析工具、手动更新入口、手动新增入口、浏览器验证 Cookie 回收入口。
- 不修改数据库结构、自动拖动算法、人工拖动算法、订单和发货业务逻辑。
